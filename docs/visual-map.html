IT · once a month

The export arrives

Each month IT downloads the staff permissions export, a CSV file of about 5,000 rows, and uploads it. Each row is one permission one staff member holds: which app it belongs to, what it's called, and whether it was given to them directly or comes with their position.

Example rows with a made-up name. The real export also has StaffId and StaffEmailAddress.

Why it matters

Direct assignments are the ones the manager reviews one by one: someone gave them to this person on purpose. Position-based access comes with the job and is shown for reference.

  • frontend/src/components/it-setup/UploadPanel.tsx the upload button

The app · in a second

Checked and cleaned

Before anything else, the app reads the file and checks it:

  • It reads the text correctly, whether the file was saved by Windows or as UTF-8, so names like "Jené" keep their accents.
  • It drops the export's junk rows: a line of dashes and a "(rows affected)" footer the system adds every month.
  • It refuses files it can't use: the wrong columns, no real rows, larger than 10 MB, or not a .csv. The message says what's wrong.
4,963rows in the July file
4,961permission rows kept
2junk rows dropped
Why

An audit over an empty or wrong file would produce a report that says nothing while looking official. Refusing it outright is safer than quietly carrying on.

In the code
  • backend/app/services/uploaded_dataset.py process_upload
  • backend/tests/test_csv_reading.py the encoding checks

The app · for this upload only

A private session starts

The upload gets its own session: a long random key, and the file's data held in the server's memory. The browser shows the key with every request, and only ever sees its own data.

session key · kQ3vR8…(43 characters)…xT2
In memory only Never written to disk One per upload
Why

Two people auditing at the same time can't see or overwrite each other's work. The data holds real staff permissions, so it never touches the server's disk.

In the code
  • backend/app/services/session_service.py
  • current_session in backend/app/api/routes.py

The app · for every staff member

The audit tree

Each staff member's rows are arranged into a tree: where the access comes from, then which app, then each permission.

Every permission gets an ID, a fingerprint worked out from the row itself. Highlights and decisions are all recorded against these IDs.

Why fingerprints

The same file always produces the same IDs. If the server restarts mid-audit, uploading the same file again brings back every selection and decision still open in the browser.

In the code
  • build_audit_tree and _leaf_id in backend/app/services/uploaded_dataset.py
  • POST /api/audit-tree
5
IT · step 1 on screen

IT setup

IT names the department and month, then picks the staff to review. They can search by name, filter by position, or search for a permission to find everyone who holds it.

Anything the manager should look at closely gets a highlight, with an optional note:

Open Charts
Catapult EHR · Direct Assignment
★ Highlighted IT: Granted for a temporary project; confirm it's still needed.
Where highlights go

A highlight follows the permission through the manager's review, the report and the printable packet, because it's attached to the permission's ID.

In the code
  • frontend/src/components/it-setup/ one file per part of this step
  • HighlightTree.tsx, PermissionSearch.tsx

Manager · step 2 on screen

Manager audit

The manager marks each permission Keep or Revoke. One rule applies automatically: revoking an app's "Access" revokes the rest of that app and locks it, because without access the other permissions mean nothing.

The app · when the manager clicks Finalize

The report

Finalize sends every decision to the server. The server applies the Access rule again itself, then counts and writes the completed report: every staff member's access with each decision, highlight and note.

The server is the record

The screen's copy of the rule only makes clicks feel instant. The report's numbers always come from the server, and two separate checks confirm it counts the way it should.

In the code
  • backend/app/services/report_service.py
  • checks/ the two comparison checks

Step 3 on screen

What comes out

The report

Read-only, opens in the browser and can be downloaded. The record of the audit.

Review packet

A printable page per staff member, with Keep and Revoke boxes and highlights marked.

CSV export

The selected staff's rows, with department and date added. Cells can't run as spreadsheet formulas.

In the code
  • report_service.py, document_service.py, export_service.py in backend/app/services/
9
Automatically

The session ends

A session ends when the user clicks Start a new audit, uploads another file, or leaves it idle for 60 minutes. Then the server forgets it.

Left on the server

Nothing. No file, no database, no copy of the upload.

Kept by the people involved

Whatever they downloaded: the report, the packet, the export.

In the code
  • DELETE /api/session, and the idle sweep in session_service.py
Around the app

How it reaches people

The whole app ships as one container. A secure front door sits in front of it, and everything a user does passes through that door.

Browser

IT and managers use the app in a normal web browser.

→

Secure front door

Encrypts the connection (HTTPS). On AWS this is a load balancer; on a virtual machine, nginx on that machine. Sign-in will live here.

→

The container

Web server: the pages Backend: sessions, tree, report

Only the front door can reach it

The container trusts what the front door tells it, so nothing else may connect to it.

Exactly one copy

Sessions live in one container's memory. A second copy couldn't see them.

1 GB of memory, no swap

Uploads stay in memory. Swap would write them to disk.

A restart ends every session

Users re-upload the same file, and their open audit comes back.
